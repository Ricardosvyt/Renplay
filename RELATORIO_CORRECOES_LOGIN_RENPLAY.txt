1. PROBLEMAS CONFIRMADOS E CAUSA RAIZ
================================================================================

Durante a auditoria especializada de codigo, foram confirmados quatro problemas criticos e estruturais na camada de autenticacao:

PROBLEMA 1: CONFIANCA INDEVIDA EM CABECALHOS HTTP DE IP
- Causa Raiz: A implementacao anterior em `src/lib/client-ip.ts` inspecionava cabecalhos como `cf-connecting-ip`, `x-real-ip` e `x-forwarded-for` aceitando qualquer valor que representasse um IP valido, sem validar a fronteira de confianca da infraestrutura.
- Mecanica da Falha: Em aplicacoes hospedadas na Vercel, a borda da plataforma sobrescreve exclusivamente `x-vercel-forwarded-for`. Cabecalhos como `cf-connecting-ip` ou `x-real-ip` enviados por clientes externos podiam passar intactos se Cloudflare nao estivesse ativo como proxy autoritativo, permitindo que um atacante falsificasse seu IP simplesmente inserindo `CF-Connecting-IP: 1.2.3.4` para contornar contadores de rate limit.

PROBLEMA 2: USO DE 127.0.0.1 COMO FALLBACK FICTICIO PARA CLIENTES DESCONHECIDOS
- Causa Raiz: Quando a aplicacao nao encontrava um cabecalho reconhecido, a funcao `extractClientIp` retornava hardcoded o endereco de loopback `127.0.0.1`.
- Mecanica da Falha: Tratar clientes externos sem cabecalho como `127.0.0.1` criava dois riscos graves:
  a) Colisao de Identidade: Varios usuarios externos nao identificados colidiam na mesma chave de rate limit (`auth:login:ip:<hash(127.0.0.1)>`), permitindo que um invasor bloqueasse todos os demais;
  b) Falsa Concessao de Confianca: Identificar trafego externo como loopback local viola o principio de menor privilegio e pode burlar regras de rede internas.

PROBLEMA 3: CONDICAO DE CORRIDA (TOCTOU) NO RATE LIMITING
- Causa Raiz: O fluxo anterior operava em duas etapas desconectadas:
  1) `checkAuthRateLimit` executava um `SELECT` simples na tabela `rp_limits`;
  2) Apenas se o login falhasse, a rota invocava `recordAuthFailure` (`INSERT ... ON CONFLICT DO UPDATE`).
- Mecanica da Falha: Time-of-Check to Time-of-Use (TOCTOU). Se um atacante disparasse 50 ou 100 requisicoes simultaneas em paralelo contra a mesma conta, todas as 50 requisicoes executavam o `SELECT` antes que qualquer falha fosse computada. Como todas liam `hits = 0` (ou valor abaixo do limite), TODAS as 50 eram admitidas e calculavam hashes Argon2id simultaneamente, contornando o limite de 5 tentativas e sobrecarregando a CPU serverless.

PROBLEMA 4: LIMPEZA ASSINCRONA NAO GARANTIDA (FIRE-AND-FORGET) NA TABELA rp_limits
- Causa Raiz: A remocao de registros expirados da tabela `rp_limits` era executada via consulta assincrona desatrelada com captura de erro: `db.query(...).catch(() => undefined)`.
- Mecanica da Falha: No runtime serverless da Vercel (AWS Lambda / Edge), o ciclo de vida do processo e congelado assim que a resposta HTTP e enviada ao cliente. Promises soltas (`fire-and-forget`) sao interrompidas imediatamente, resultando na falha silenciosa da limpeza e em inchaco continuo (table bloat) da tabela `rp_limits`.

+++ CODIGO NOVO (Fronteira Vercel estrita e sem fallback ficticio) +++
```typescript
// Novo src/lib/client-ip.ts
export function extractClientIp(request: Request): ClientIpInfo {
  const headers = request.headers;
  const isProduction = process.env.NODE_ENV === "production" || process.env.VERCEL === "1";
  const trustCloudflare = process.env.TRUST_CLOUDFLARE_PROXY === "true";

  // 1. Cabecalho Autoritativo Vercel (Garantido pela infraestrutura na borda)
  const vercelHeader = headers.get("x-vercel-forwarded-for");
  if (vercelHeader) {
    const candidate = vercelHeader.split(",")[0]?.trim();
    if (candidate) {
      const normalized = normalizeIp(candidate);
      if (normalized) {
        return {
          ip: candidate,
          normalizedIp: normalized,
          sourceHeader: "x-vercel-forwarded-for",
          isReliable: true,
          ipHash: hashIp(normalized),
          maskedIp: maskIp(normalized),
        };
      }
    }
  }

  // 2. Cloudflare (Exige ativacao explicita via variavel de ambiente)
  if (trustCloudflare) {
    const cfHeader = headers.get("cf-connecting-ip");
    if (cfHeader) {
      const normalized = normalizeIp(cfHeader);
      if (normalized) {
        return {
          ip: cfHeader,
          normalizedIp: normalized,
          sourceHeader: "cf-connecting-ip",
          isReliable: true,
          ipHash: hashIp(normalized),
          maskedIp: maskIp(normalized),
        };
      }
    }
  }

  // 3. Modo Desenvolvimento / Testes Locais Apenas
  if (!isProduction) {
    const forwarded = headers.get("x-forwarded-for");
    if (forwarded) {
      const candidate = forwarded.split(",")[0]?.trim();
      const normalized = candidate ? normalizeIp(candidate) : null;
      if (normalized) {
        return {
          ip: candidate,
          normalizedIp: normalized,
          sourceHeader: "x-forwarded-for",
          isReliable: false,
          ipHash: hashIp(normalized),
          maskedIp: maskIp(normalized),
        };
      }
    }
  }

  // 4. Ausencia de IP Confiavel: EXPLICITAMENTE NULL. NUNCA 127.0.0.1
  return {
    ip: null,
    normalizedIp: null,
    sourceHeader: null,
    isReliable: false,
    ipHash: null,
    maskedIp: "unverified-origin",
  };
}
```

+++ CODIGO NOVO (Reserva atomica com bloqueio por linha no PostgreSQL) +++
```typescript
// Novo src/lib/auth-rate-limit.ts
export async function reserveAuthAttempt(
  request: Request,
  action: string,
  normalizedIdentifier: string
): Promise<RateLimitCheckResult> {
  const { normalizedIp } = extractClientIp(request);
  const { pairKey, ipKey, distribKey, isIpTrusted } = getRateLimitKeys(action, normalizedIp, normalizedIdentifier);

  // Instrucao atomica que serializa requisicoes simultaneas no PostgreSQL
  const upsertSql = `
    INSERT INTO rp_limits (key, hits, resets_at)
    VALUES ($1, 1, now() + interval '15 minutes')
    ON CONFLICT (key) DO UPDATE SET
      hits = CASE WHEN rp_limits.resets_at <= now() THEN 1 ELSE rp_limits.hits + 1 END,
      resets_at = CASE WHEN rp_limits.resets_at <= now() THEN now() + interval '15 minutes' ELSE rp_limits.resets_at END
    RETURNING hits, GREATEST(1, EXTRACT(EPOCH FROM (resets_at - now()))::int) AS remaining_seconds;
  `;

  try {
    const db = getDb();
    const [pairResult, ipResult] = await Promise.all([
      db.query<{ hits: number; remaining_seconds: number }>(upsertSql, [pairKey]),
      db.query<{ hits: number; remaining_seconds: number }>(upsertSql, [ipKey]),
    ]);

    const pairHits = pairResult.rows[0]?.hits ?? 1;
    const ipHits = ipResult.rows[0]?.hits ?? 1;

    // Se o incremento atomico ultrapassou o limite, rejeita IMEDIATAMENTE (HTTP 429)
    if (pairHits > MAX_ATTEMPTS_PER_PAIR) {
      return { allowed: false, retryAfter: pairResult.rows[0].remaining_seconds, reason: "PAIR_EXCEEDED" };
    }

    const ipMax = isIpTrusted ? MAX_ATTEMPTS_PER_IP : MAX_UNTRUSTED_GLOBAL_ATTEMPTS;
    if (ipHits > ipMax) {
      return { allowed: false, retryAfter: ipResult.rows[0].remaining_seconds, reason: "IP_EXCEEDED" };
    }

    return { allowed: true, retryAfter: 0, shouldTarpit: false, tarpitMs: 0 };
  } catch (err) {
    // Falha de banco = Fail Closed seguro com HTTP 503
    return { allowed: false, retryAfter: 60, isServiceUnavailable: true, reason: "DB_UNAVAILABLE" };
  }
}
```

2.3. LIMPEZA GARANTIDA EM LOTES (src/lib/auth-rate-limit.ts e Cron Route)

+++ CODIGO NOVO (src/lib/auth-rate-limit.ts - cleanupExpiredLimits) +++
```typescript
export async function cleanupExpiredLimits(dbPool?: Pool, batchSize = 1000): Promise<number> {
  const db = dbPool ?? getDb();
  try {
    // Limpeza em lote limitada utilizando o indice rp_limits_reset_idx
    const result = await db.query(
      `DELETE FROM rp_limits
        WHERE ctid IN (
          SELECT ctid FROM rp_limits
           WHERE resets_at < now() - interval '1 hour'
           LIMIT $1
        )`,
      [batchSize]
    );
    return result.rowCount ?? 0;
  } catch (err) {
    console.error("Erro ao limpar registros expirados de rp_limits:", err);
    return 0;
  }
}
```

+++ ROTA OFICIAL DE CRON (src/app/api/cron/cleanup-limits/route.ts) +++
```typescript
export async function GET(request: Request) {
  const isVercelCron = request.headers.get("x-vercel-cron") === "1";
  const authHeader = request.headers.get("authorization") || "";
  const cronSecret = process.env.CRON_SECRET;

  const isAuthorized =
    isVercelCron ||
    (cronSecret && authHeader === `Bearer ${cronSecret}`) ||
    process.env.NODE_ENV !== "production";

  if (!isAuthorized) {
    return NextResponse.json({ error: "Acesso não autorizado." }, { status: 401 });
  }

  const db = getDb();
  const deletedCount = await cleanupExpiredLimits(db, 2000);
  return NextResponse.json({ success: true, cleanedExpiredRows: deletedCount });
}
```

5. CONFIGURACOES NECESSARIAS NA VERCEL
================================================================================

Para garantir a operacao ideal da infraestrutura de seguranca em producao na Vercel:

1. Cabecalho de IP Nativo:
   - Nenhuma configuracao adicional e necessária para o cabecalho de IP basico. A Vercel injeta `x-vercel-forwarded-for` automaticamente em todos os planos (Hobby e Pro).

2. Uso Opcional de Cloudflare a Frente da Vercel:
   - Se o projeto utilizar Cloudflare na frente do dominio, defina a seguinte variavel de ambiente no painel da Vercel (Project Settings -> Environment Variables):
     `TRUST_CLOUDFLARE_PROXY=true`
   - Se essa variavel nao for definida, o sistema ignora deliberadamente `cf-connecting-ip`, protegendo contra injecoes falsas.

3. Vercel Cron Jobs (Limpeza Agendada de rp_limits):
   - O arquivo `vercel.json` foi adicionado na raiz do projeto com o conteudo:
     ```json
     {
       "crons": [
         {
           "path": "/api/cron/cleanup-limits",
           "schedule": "0 * * * *"
         }
       ]
     }
     ```
   - No plano Vercel Hobby, e permitida 1 execucao de cron por dia; no plano Pro, execucoes horarias sao suportadas nativamente.
   - Seguranca do Cron: Defina a variavel de ambiente `CRON_SECRET` no painel da Vercel para autorizar chamadas manuais ou externas caso desejado. A Vercel inclui automaticamente o cabecalho `x-vercel-cron: 1` em suas invocacoes internas.

7. RISCOS RESIDUAIS CONHECIDOS
================================================================================

Em observancia a diretriz de rigor tecnico e transparencia, nao se declara seguranca absoluta. Permanecem os seguintes riscos residuais operacionais:

1. Credential Stuffing com Botnets Residenciais Massivas:
   - Atacantes utilizando redes de computadores zumbis onde cada IP tenta apenas 1 ou 2 senhas podem dificultar o bloqueio por IP puro. O micro-tarpit mitiga a velocidade, mas o fator definitivo de protecao contra esse vetor e a implantacao de Segundo Fator de Autenticacao (MFA / 2FA).
2. Ausencia de MFA / 2FA no Momento Atual:
   - Por solicitacao de escopo, 2FA nao foi adicionado nesta fase. Recomenda-se sua inclusao no roadmap futuro.
3. Cold Starts de Funcoes Serverless:
   - A inicializacao fria de contêineres serverless pode adicionar variacoes pontuais na latencia geral da requisicao, embora sem quebrar a integridade criptografica.
